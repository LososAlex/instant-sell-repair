# repair-worker (mm2-swap)

Воркер автопочинки ботов mm2-swap с тикет-системой. Крутится на сервере, опрашивает прод, сам чинит что может, остальное — через очередь тикетов `repair_queue` (как в прод-ФС).

Статус: **набросок** (часть допущений помечена ниже).

## Что делает

Бесконечный цикл (`POLL_INTERVAL_SEC`, по умолчанию 600 с = 10 мин): `GET /api/v1/bots/broken`, по каждому боту — как в прод-ФС.

Бот матчится с mongo `accounts_p2p` по `roblox_id` (оттуда берём куки — туда воркеры пишут свежее). Дальше смотрим **последний тикет** бота:

1. **Активный тикет** (`queued`/`in_progress`) → пропуск, его чинят.
2. **Тикет `fixed`** (фиксер обновил `accounts_p2p`) → до-применяем `repair`, статус тикета **не меняем** (как в ФС); бот после repair уходит из брокенов:
   - `reason = captcha` → `repair` только с `bot_id` (без данных);
   - `reason = refresh_invalid` (куки) → `repair` с `roblox_auth = cookies[0]` (свежие).
3. **Тикета нет / `failed`** → обычный путь по `state`:

| `state` | Условие | Действие |
|---|---|---|
| `BROKEN` | `cookies ≥ 2` | Автопочинка: `repair` с `cookies[1]`; при успехе удаляем `cookies[0]` (ротация). `repair != 200` → retry на следующих циклах; после `MAX_REPAIR_ATTEMPTS` (3) подряд → алерт в тред `general` и **продолжаем пробовать** (тикет не заводим) |
| `BROKEN` | `cookies < 2` | Тикет `refresh_invalid` (нужна регенерация кук) |
| `CAPTCHA` | — | Тикет `captcha` (ручная починка) |
| иной | — | Пропуск с логом |

Счётчик неудачных авто-починок (`repair != 200`) — в памяти процесса, по попытке за цикл. Каждые 3 неудачи подряд → одно сообщение в `general`, затем счётчик сбрасывается и ретраи продолжаются. При перезапуске воркера сбрасывается.

При `fixed`-тикете после успешного `repair` тикет → `status = resolved` (**и капча, и куки**). Это нужно, чтобы **повторный слом** бота трактовался как свежий инцидент: последний тикет будет `resolved` (не `fixed`), и воркер пойдёт обычным путём — заведёт новый тикет / авто-починит новой кукой, — а не зациклит применение старой куки из старого тикета.

Прод-uuid для `/repair` берём прямо из `/broken` (поле `bot_id`) — Postgres не нужен.

### Списание замодеренных INVENTORY → `DEAD` (с 02.10)

До починки, каждый цикл: бот из `/broken` с `type = INVENTORY`, у которого по нику есть **незакрытый**
тикет `moderated` (`queued` / `in_progress`), уходит в `DEAD` через
`PATCH /api/v1/bots/{roblox_account_id}/dead` с заголовком `x-cv-key` (`CV_KEY` в `.env`). Ручка
ветеранского флоу из `swaps-back` (`modules/bots/cv-dead`): ставит только `state = DEAD`, повтор —
no-op. Дальше такого бота не чиним. Событие `bot_dead` уходит в Grafana, список — в `general`.

- Зачем: аккаунт замодерен Roblox и не чинится ничем, а `BROKEN` держит место в лимите парка, и ротатор
  не может залить замену. После `DEAD` ротатор сам переведёт запись в `done` в mongo.
- Почему безопасно: у `INVENTORY` нет стока (на 01.10 у 180 живых — 0 предметов). `TRADE` не трогаем.
  Откат — `PATCH /bots/repair` (переводит в `OFFLINE`, на состояние не смотрит).
- После `DEAD` незакрытые тикеты `moderated` бота закрываем: `status = resolved`, `resolved_at`,
  в `notes` — что бот списан. Если `DEAD` не прошёл, тикет остаётся открытым, попытка повторится на
  следующем цикле.
- Предохранитель `MAX_DEAD_PER_TICK` (20): больше за цикл не списываем, о лишних пишем в `general`.
- Пустой `CV_KEY` — шаг выключен.

### Игра бота (с 02.10)

`/broken` отдаёт ботов **всех** игр свопа (MM2 и Adopt). По полю `game` (число enum `Games`:
4 — MM2, 0 — Adopt) берём из `GAMES` в `config.py`:

- метку — в начало каждого сообщения в телеграм (`[MM2] <b>ник</b> …`), в список новых брокенов и
  колонкой «игра» в `/status`, где в заголовке ещё и разбивка брокенов по играм;
- `stage` — в каждое событие Grafana, тот же, что шлёт ротатор этой игры (`mm2-swap-production`,
  `adopt-swap-production`). Плюс поле `game` с меткой.

Игры нет в `GAMES` — метка `game=N`, `stage` — общий `STAGE`.

## Тикеты (`repair_queue`)

Та же коллекция `mm-inventory.repair_queue`, что у ФС, та же схема и тот же лайфцикл. Отличие свопа: **`priority` всегда 1**.

- `bot_id` тикета = **mongo `_id` записи бота** (общий для `accounts_p2p` и `mm2_swap`) — ключ дедупа и поиска бота фиксером.
- Лайфцикл: `queued` → `in_progress` → `fixed` (ставит внешний Fixer). Воркер свой статус не выставляет — как в ФС, просто до-применяет `repair`, пока бот в брокенах.
- Дедуп: не создаём второй тикет, пока есть активный (`queued`/`in_progress`).
- Дискриминатор не нужен: свопный `/broken` отдаёт только свопных ботов, ФС-тикеты воркер не трогает.

## Логирование в Grafana

Тот же механизм, что в прод-ФС: воркер шлёт события `POST {MONITORING_URL}/event` (заголовок `x-api-key`), сервис пишет в Grafana-БД `bot_events`. `stage = production` (как в ФС) — свопных ботов Максим выделит в группу на стороне Grafana. Если `MONITORING_URL` пуст — `send_event` no-op (воркер работает без телеметрии).

| Событие (`event_type`) | Когда |
|---|---|
| `bot_cookie_updated` (`mode=auto_refresh`) | Автопочинка кукой `cookies[1]` удалась |
| `bot_cookie_updated` (`mode=ticket_fixed`) | Применили `cookies[0]` по решённому тикету |
| `bot_captcha_repaired` (`mode=ticket_fixed`) | Применили repair по решённому капча-тикету |
| `bot_broken_refresh` (`reason=cookies<2`) | Завели тикет на регенерацию кук |
| `bot_in_roblox_captcha` | Завели тикет на капчу |
| `bot_not_found_mongo` | Бот из `/broken` не найден в `accounts_p2p` |

Имена `event_type` совпадают с ФС, чтобы переиспользовать готовые панели/запросы.

## Логи

`logging` пишет одновременно в консоль и в `logs/repair.log` (ротация: 5 МБ × 5 файлов). Все модули (`repair_worker`, `repair_queue`, `monitoring`, `notifications`) логируют сюда же.

## Телеграм-алерты

`notifications.py` шлёт сообщения в `TELEGRAM_CHAT_ID`, в топик по `THREAD_IDS` (форум-группа). Свой Bot API-сервер — `TELEGRAM_API_BASE`. На голом `requests` (без aiogram). Пустой токен — `send_message` no-op.

| Событие | Топик (`thread_key`) |
|---|---|
| Авто-починка кукой `cookies[1]` | `refresh_updated` |
| Применён `fixed`-тикет (куки) | `refresh_updated` |
| Применён `fixed`-тикет (капча) | `captcha_in_roblox` |
| Заведён тикет на куки (`cookies<2`) | `broken_refresh` |
| Заведён тикет на капчу | `captcha_in_roblox` |
| Бот из `/broken` не найден в `accounts_p2p` | `broken_cookie` |
| Новые брокены за цикл (батч) | `new_brokens_in_prod` |
| Авто-починка кук не удалась 3 раза подряд | `general` |

## Запуск

```bat
run.bat
```

Первый запуск сам создаёт `venv` и ставит зависимости из `requirements.txt`, затем гоняет `repair_worker.py` в цикле с авторестартом. Нужен только установленный Python в `PATH`.

## Решения и допущения

- **enable после repair — НЕ здесь.** Поднятие бота в игру после починки делает бэк. Воркер `enable` не дёргает (решено 2026-06-30).
- **`fixed` ставят воркеры починки.** Куки регенерят отдельные воркеры и переводят тикет `queued → fixed`; наш воркер только до-применяет `repair`.
- **`resolved` после применения — симметрично для капчи и кук.** `fixed`-тикет после успешного `repair` переводим в `resolved`. Так повторный слом бота видит прошлый тикет завершённым и идёт свежим путём (новый тикет / авто-починка новой кукой), а не зацикливает применение старой куки. Заменяет механизм ФС с анализом трейдов, которого у нас нет (решено 2026-06-30).
- **Приватный сервер / новые states.** ФС разбирает state `4` (битая кука приватки) и `9` (плохой приватный сервер). У свопа сейчас только `BROKEN`/`CAPTCHA` — добавим обработку, когда появятся новые states.
- **attempts в памяти.** Счётчик неудачных авто-починок не персистится — при рестарте воркера обнуляется. Для эскалации в тикет этого достаточно (3 неудачи за ~30 мин).
